## 시나리오 정의

- 최대 5종 제품이 섞여 있다. 인스턴스 분리에 더해 **"어느 제품인가"** 까지 맞혀야 한다.
- 제품 유형은 [ONE]과 같은 세 가지를 섞는다. [ONE]에서 고른 제품을 포함하면 촬영과 라벨을 재사용할 수 있다.
- 주지표: 클래스별 mAP + 매칭된 인스턴스의 분류 정확도. 마스크 오류와 분류 오류를 분리해서 본다.

## 추천

| 단계 | 방법 | 유형 | 학습 | 라이선스 | 4060L 속도 (추론) |
|---|---|---|---|---|---|
| **운영 1순위** | **RF-DETR-Seg** 다중 클래스 | [E2E] | 클래스당 50~100장, 총 200~500장 출발점(추론) | Apache-2.0 (직접 확인) | 수십 ms |
| 학습 전 (매칭형) | m1/m2 제안 + **DINOv2 마스크 임베딩 kNN** | [PM] | 제품당 레퍼런스 5~20장 | Apache-2.0 | ~1.0~1.1s |
| 학습 전 (메모리뱅크형) | **no-time-to-train** (SAM2 + DINOv2) | [PM] | 실사진 레퍼런스 | Apache-2.0 | 원본 2~3s → 제안기 교체 필요 |
| 학습 전 (사진 등록형) | OWLv2 예시 이미지 다중 쿼리 → SAM2 | [DS] | 제품당 1~수 장 | Apache-2.0 | 쿼리 수에 비례 |
| 학습 전 (어휘형) | SAM3 제품별 텍스트 | [E2E] | 없음 | SAM License | 5종이면 1s 초과 가능(추론) |

**권장 흐름 (추론):** [ONE]과 같다. [PM] 또는 OWLv2로 자동 라벨 → 검수 → RF-DETR-Seg 다중 클래스 학습.

**핵심 관찰 (추론):** DINO 특징은 "무슨 제품인가"는 잘 구분하지만 "같은 제품 두 개의 경계"는 거의 구분하지 못한다. [FEW]에서 DINO의 역할은 **분류**이고, 인스턴스 분리 품질은 제안기가 결정한다.

**0.5s를 맞추는 [PM] 후보:** cnos25(YOLOE + DINOv3, RTX 4090 0.134s 확인 → 4060L 0.3~0.4s 추론)가 유일하다. 하지만 YOLOE는 AGPL이고 DINOv3는 Meta 자체 라이선스라 이중 감점이다. 제안기를 Apache 모델로 바꾸면 쓸 수 있다(추론).

## DINOv2 vs DINOv3 (미해결)

- 라이선스 (확인): DINOv2는 Apache-2.0이다. DINOv3는 "DINOv3 License"(Meta 자체)이고, 군사 용도 금지, 재배포 시 계약서 동봉, 가중치 신청 절차가 있다.
- 성능은 문헌이 엇갈린다 (확인): no-time-to-train 논문은 v3가 유사 클래스 구분에서 약하다고 했고, cnos25는 v3로 BOP 2025 수상을 했다.
- 기본값은 DINOv2로 두고, 3단계에서 v3와 A/B하는 것을 제안한다(추론).

## 입력 모달리티

[ONE]과 같다. 강체는 [RGB-D-N] 이득이 크고, 반사 부품은 깊이 신뢰도 가중이 전제이며, 파우치는 이득이 작다(추론). 분류에는 RGB 외관이 핵심이라, 깊이·법선은 분리 단계에만 쓴다(추론).

## 데이터 (`data/dataset-plan.md` 5장)

- 테스트 40장(5종 혼합 + 2~3종 혼합 일부)과 제품 1종을 바꾼 "신규 제품" 세트 10장.
- 학습: 혼합 실측 100~150장 + [ONE] 단품 데이터 재사용 + 합성 3,000~5,000장(추론).

## 3단계에서 확인할 것

1. DINOv2 vs DINOv3 매칭 정확도 (같은 제안기 기준)
2. 학습 전 [PM] 방법으로 만든 자동 라벨의 정확도 (검수 부담 추정)
3. 신규 제품 교체 시 재학습 비용 vs [PM] 레퍼런스 교체 비용
